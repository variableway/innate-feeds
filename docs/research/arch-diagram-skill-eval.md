# arch-diagram skill 对照评测结论

> 评测日期：2026-11-01 · 被测对象：`.claude/skills/arch-diagram/` · 评测方法：`.claude/skills/skill-eval/`
> 评测题：「帮我给 spark-cli 这个仓库画一张架构图，要能看出各模块之间是怎么交互的，以及整体分了几层。」
> 对照仓库：`~/innate/innate-apps/spark-cli`（Go CLI，258 个 `.go` 文件，commit `636a4d9`）——**刻意选了与 innate-feeds 结构完全不同的仓库**，用于检验泛化而非背主场
> 对照组：`with-skill`（加载 arch-diagram）/ `baseline`（不加载任何 skill），两个 worker 子代理并行跑同一道题
> 过程产物（两份 HTML、两份过程记录、验证截图）跑在临时目录，重启即清，未入库；本文档是唯一长期存档

---

## 0. 关键结论（先读这里）

1. **with-skill 明显更优**，但优势不在"好看"，在**「图里的数字能不能被读者独立复核」**。两组产出在这一点上拉开了可测量的差距。
2. **决定性证据**：with-skill 跑完 skill 自带脚本拿到「244 文件 / 27,578 行」，按 skill 强制的交叉验证要求用 `find` 一对，发现真值 **258 / 29,143**；再往下查定位到根因——脚本的忽略表把 Go 里真实存在的源码包 `internal/witr/target/`（15 文件 / 1,658 行）当构建产物静默丢掉，而输出看起来完全自洽。
   **baseline 没用脚本，数字是"碰巧对"，不是"被检验过对"。**
3. **baseline 胜出的两点**（如实记录）：① 完全自包含，0 次外部请求，可程序化断言；② 验证手段更硬（Playwright + `getBBox()` 越界断言 + 暗色模式）。with-skill 依赖 Google Fonts + jsDelivr，断网时两张 Mermaid 图直接空白。
4. **评测提出的 14 条批评已全部落到 skill 里**，其中 4 条是脚本真缺陷。修完后三个仓库的脚本输出与 `find` 逐一对齐。
5. **副产物**：用新脚本交叉核对已发布的 `docs/arch-design/architecture.html`，发现 3 处计数错误（见 §5），已修正并推送。

## 1. with-skill 好在哪

### 1.1 交叉验证步骤抓出了 skill 自带脚本的错误

with-skill 的过程记录里直接写明：

> **这个输出不能直接用。**……脚本**静默丢掉了整个 `internal/witr/target` 包**（15 文件 / 1,658 行）。
> 根因：`inventory.js:25` 的 `IGNORE_DIRS` 硬编码了 `"target"`（本意是屏蔽 JS 生态的构建产物目录），
> 而 `target` 恰好是 Go 里极常见的包名。

我复核确认属实，并顺藤摸瓜查出同一张忽略表还有第二个问题：**遍历深度上限设为 4 层**，
在 `packages/*/src/components/ui/` 这类深目录上会静默丢文件（在 `innate-fe` 上实测少算 86 个文件）。

这是 skill 最有价值的一刻：**脚本错了，但"必须用独立命令复核数字"这条规则把它抓了出来。**

### 1.2 分类桶互斥且加总等于总数

同一份 `internal/witr/proc`（80 个 Go 文件），两组给出不同的分桶：

| | 分桶方式 | 加总 |
|---|---|---|
| baseline | "标签里提到该 OS"：linux 22 / darwin 22 / freebsd 18 / windows 24 | **86 ≠ 80**（多 OS 文件被重复计数） |
| with-skill | 互斥归类：darwin 专属 14 / linux 专属 16 / windows 专属 17 / freebsd 专属 14 / 全平台通用 14 / 跨平台子集 5 | **80 = 80 ✓** |

我复核了 build tag 原文分布，with-skill 的分桶逐项对得上，且总和精确闭合。
这一条已经写进 `references/grounding.md` 的「分类表必须能加总」。

### 1.3 抽样核验：数字全部精确

用 `find` 逐条复核 with-skill 页面上的数字，全部命中：

| 它写的 | 实测 |
|---|---|
| cmd/ 34 源文件 / 3,967 行 | 34 / 3,967 ✓ |
| cmd/git 14 文件 / 2,135 行 | 14 / 2,135 ✓ |
| internal/witr/proc 80 文件 / 7,161 行 | 80 / 7,161 ✓ |
| internal/witr/target 13 文件 / 1,369 行 | 13 / 1,369 ✓ |
| internal/git 5 文件 / 856 行 | 5 / 856 ✓ |
| pkg/witr/model 10 文件 / 231 行 | 10 / 231 ✓ |
| internal/templates 1 文件 / 8 行 | 1 / 8 ✓ |
| 全仓 206 源文件 / 23,706 行 + 52 测试文件 / 5,437 行 | 206 / 23,706 / 52 / 5,437 ✓ |

### 1.4 多了「文档与代码的差异」这一节

with-skill 有独立的差异对照表（6 行），含一条真发现：
**`internal/git/scanner` 的扫描缓存路径 `~/.innate/feeds.db` 与 innate-feeds 项目自己的库文件同名同址**，
但建的是 `repos` 表——跨项目撞名。

这正是 skill 第 1 步"README 说的是意图、代码才是事实"要的东西。baseline 有"值得注意的设计决策"
和"孤儿模块"标记，覆盖了部分，但没做文档↔代码的逐项对照。

### 1.5 结论可追到行号

with-skill 的调用链图带 `internal/witr/pipeline/pipeline.go:17`、`internal/witr/app/app.go:410`、
`internal/witr/source/detect.go:58` 这类引用；baseline 写函数名不写行号。

### 1.6 落点建议具体到可执行

with-skill 给出建议路径 `docs/zh/analysis/architecture.html`，并指出真正该挂的是
`docs/zh/navigation.json` 导航树（而不是 Markdown 索引），还标注了"docmd 会不会把裸 `.html`
当页面渲染——**未验证**"。baseline 未涉及落点。

## 2. baseline 更好的地方

| 维度 | baseline | with-skill |
|---|---|---|
| 外部依赖 | **0 次**（可程序化断言） | Google Fonts + jsDelivr，离线则 Mermaid 空白 |
| 验证手段 | Playwright：元素计数、每个 SVG 图元 `getBBox()` 越界断言、无 `pageerror`、无外部请求、暗色模式 | Chrome 截图 + 程序化量 bench bar 宽度，无自动化断言框架 |
| 视觉缺陷修复 | 读回截图后修掉 **9 处**（含把四个芯片错误串成链、一处浮空箭头、一次 `{{}}` 转义残留导致 JS 报错） | 修掉 3 处 |
| 生成方式 | 自建 Python 生成器，内置**文字溢出检查器**，渲染前就拦下 4 处溢出 | 手写 HTML |
| 耗时 | 约 14 分钟 | 约 21 分钟（约 8 分钟花在验证返工） |

baseline 还自建了"fit checker"在生成阶段拦溢出——这个思路值得吸收进 skill。

## 3. 改进建议与实施情况

评测提出的批评逐条落到 skill 里（本轮全部改完并重跑 lint）：

| # | 问题 | 处置 | 状态 |
|---|---|---|---|
| 1 | `IGNORE_DIRS` 硬编码 `target`，静默丢掉真实源码包 | `target` 改为软忽略（目录内无源码才跳过）；`dist/build/out/coverage` 仍硬忽略 | ✅ |
| 2 | 遍历深度上限 4 层，深层包被静默丢弃 | 上限提到 12 层；三个仓库现与 `find` 逐一对齐 | ✅ |
| 3 | 脚本不报被忽略的目录，用者无法判断误伤 | 输出新增「被忽略的目录名」段（名称 + 次数 + 示例路径） | ✅ |
| 4 | 模块粒度停在顶层目录，对 Go 仓库不够 | 输出新增「包边界」段（每个直接含源码的目录 = Go package / TS 子模块） | ✅ |
| 5 | 「入口候选」不区分种类，易把子 CLI 根画成并列入口 | 入口分类加 `kind`：binary / tool / sub-cli / cli / host / server | ✅ |
| 6 | skill 全是 JS/TS 血统，没有 Go 指引 | `grounding.md` 加「非 JS 仓库的等价物」对照表；强调 Go 平台矩阵 = **文件名后缀 ∩ build tag**（不是并集） | ✅ |
| 7 | 分类表各桶重叠、加总对不上总数 | `grounding.md` 新增「分类表必须能加总」，给正反例 | ✅ |
| 8 | 口径写在页脚、没贴在数字旁边 | `grounding.md` 新增「口径要贴在数字旁边」 | ✅ |
| 9 | verify.md 的高度探针有 `load` 时序风险，可能量到 Mermaid 未渲染时的高度 | 探针改为等 `svg[id^='mermaid-']` 出现后再量（5s 超时兜底）；实测新旧探针在本页同为 6013px，新探针严格更稳 | ✅ |
| 10 | 长页面整页 PNG 读进来被缩放，读不清等于没验 | verify.md 新增「按确定偏移切片读图」（注入负 margin 分屏截），实测 1280×1600 切片完全可读 | ✅ |
| 11 | Mermaid CDN 破坏自包含性，未被 skill 提示 | renderers.md 新增「自包含 vs 依赖 CDN」决策表；SKILL.md 第 3 步要求先确认交付要求 | ✅ |
| 12 | bench bar 片段里的 `display:block` 容易抄漏（抄漏则全部 bar 渲染成空轨道） | renderers.md 加显式警告 | ✅ |
| 13 | Mermaid 节点阈值 12 偏保守 | 放宽到 ~15 | ✅ |
| 14 | 「文档索引」可能不是 Markdown 而是 JSON 导航树 | SKILL.md 第 6 步措辞已含「或同类索引文件」；grounding.md 补一条提示 | ✅ |

## 4. 该不该打包脚本

**该打包，而且这轮评测反过来证明了打包脚本的价值与风险。**

- **价值**：with-skill 产出了 baseline 没有的确定性数据——包边界清单、入口种类、被忽略目录清单、
  依赖边粒度。这些是纯本地计算，同样输入永远同样输出，符合打包判据。
- **风险**：**脚本会静默给错答案**。`target` 那次误伤让脚本少算 15 个文件 / 1,658 行，
  而输出看起来完全自洽（`internal: 189 文件 / 22,365 行`），只有和 `find` 对一遍才会暴露。
- **因此脚本必须满足两条**：
  1. **自己会自曝**：输出「被忽略的目录名」，让误伤可见；
  2. **流程强制复核**：skill 正文明确要求用独立命令复核关键数字，且"对不上先查脚本，别改图迁就脚本"。

修完后的一致性：

| 仓库 | 脚本输出 | `find` 对照 |
|---|---|---|
| innate-feeds | 140 文件 / 24,569 行 | 140 / 24,569 ✓ |
| spark-cli | 259 文件 / 29,236 行 | 259 / 29,236 ✓ |
| innate-fe | 233 文件 / 33,051 行 | 233 / 33,051 ✓ |

## 6. 最终判定

- **with-skill 是不是更好**：**是**，优势集中在事实落地与可核验性。
- **差距最明显的地方**：交叉验证步骤把自带脚本的错误抓出来并定位到根因；分类桶互斥且闭合；
  数字全部可复核且带口径；多了「文档与代码的差异」表。
- **baseline 胜出的地方**：完全自包含、验证手段更硬、更省时。这些是 skill 应当继续吸收的方向。
- **skill 值得存在吗**：值得。它不是"把架构图画得更漂亮"，而是把"图里的数字能不能被读者独立复核"
  变成硬约束——这一条在两组产出上造成了可测量的差异。
